1. The system you are building for

The system. PQ-Attest is a 3 x 2 mesh network-on-chip with six tiles, implemented on the xc7a100tcsg324-1 (Arty A7-100T board). It runs at 50 MHz (20 ns), from one clock domain. A tile may use the shared memory only after it has passed a post-quantum attestation exchange with the Root of Trust (RoT). Lane 1 (Kalash) owns:

  • the network: routers, network interfaces, credit flow control;
  • the attestation hardware: endpoint, verifier, link authentication, gates.

Your lane. You own the RISC-V CPU tile:

  • PicoRV32 (RV32IMC), with an adapter to the TMEM bus, local memories and peripherals;
  • the software that runs on it.

Your tile ends at the ten TMEM signals. Lane 1 builds the bridge from TMEM into the network.

1.4 What the network does with your requests (so your error handling is right)

  • Request types:
    • a remote write becomes a network MEM_WR_REQ (address + data, byte enables in the header);
    • a remote read becomes a MEM_RD_REQ;
    • the memory answers with MEM_WR_RESP / MEM_RD_RESP.
  • Refused tile: a request from a tile that is not authorized is refused. The Lane 1 bridge returns tmem_err for it.
  • Errors in general: an illegal address, a timeout, and a revocation in flight also return tmem_err. Your tile must turn tmem_err into a bus error (trap) to the core.
  • Tile 3 port sharing: at tile 3 the network port is shared with the attestation endpoint. A remote request can wait about 1,200 cycles while an attestation is in flight. Do not time out remote requests shorter than about 4,000 cycles (exact value comes in the Lane 1 contract).
  • Response backpressure: TMEM has none. Your tile must accept tmem_rvalid in any cycle it is raised.

4. The next 10 steps

Step 1: Fix the adapter double capture (blocking)

Root cause (confirmed in your source and with a probe):

  1. In the RESPONSE state, picorv32_adapter.sv sets mem_ready_q and returns to IDLE on the same clock edge.
  2. PicoRV32 lowers mem_valid only on the next edge, after it has sampled mem_ready (mem_xfer, picorv32.v line 373).
  3. In that cycle IDLE still sees mem_valid = 1 and captures the same request a second time.

Every request is issued twice, so every remote write reaches memory twice.

Fix (either form):

// (a) never accept a new request in the cycle the response is presented
if (state == IDLE && mem_valid && !mem_ready_q) begin  /* capture */ end

// (b) pending flag: set on capture, clear on the edge where mem_ready_q is 1
always_ff @(posedge clk)
  if (rst)                       pending <= 1'b0;
  else if (mem_ready_q)          pending <= 1'b0;
  else if (mem_valid && !pending) pending <= 1'b1;   // capture here only

Add an assertion: exactly one adapter request per core transfer.

// 'capture' = the adapter's internal "accept a new core request" signal
a_no_capture_during_ready: assert property (@(posedge clk) disable iff (rst) mem_ready_q |-> !capture);
// plus, in the testbench: count core transfers (mem_valid && mem_ready) and adapter requests; at $finish they must be equal

Verify: in tb_tile_top, count core transfers (mem_valid && mem_ready) and adapter requests separately; print both counts and compare them.

Done when:

  • core transfers = adapter requests (24 = 24 on the current program; writes 3 = 3);
  • the CPU runs past PC 0x12C in tb_tile_top and tb_two_tiles.
