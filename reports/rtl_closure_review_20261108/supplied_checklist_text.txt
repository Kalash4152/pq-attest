Project Completion & Research Readiness Checklist
Gate-by-gate execution plan from current FPGA prototype to a defensible research baseline
Prepared 8 November 2026 | Working document — update only with reproducible evidence
1. Purpose and definition of “100% complete”
This document consolidates the remaining work required to close the current PQ-Attest SoC project, establish a reproducible experimental baseline, and only then begin a research-paper programme. It is an execution checklist, not a claim that the listed work has already been completed.
“100% complete” means complete against a frozen project scope. It does not mean every optional feature (TRNG, asymmetric PQC, full-IMEM measurement, formal proof, side-channel resistance, fault-injection resistance, ASIC tapeout) has been implemented. Those are currently documented as out of scope or not established. They must either be added through an explicit scope change and verified, or remain explicit limitations.

2. Project baseline — facts to preserve
Architecture: 3×2 mesh NoC with six logical tiles: CPU0, CPU1, MEMORY, CRYPTO, RoT and SPOOF; two PicoRV32 CPU tiles.
Security path: SHA-3/KMAC/KDF-based symmetric attestation, measurement, RoT verifier, authenticated L2 link and memory authorization.
Target board: Digilent Arty A7-100T, Xilinx Artix-7 xc7a100tcsg324-1, 50 MHz.
Latest reported 7 Nov FPGA implementation: 34,987 LUT (55%), 25,276 FF, 20 BRAM36, 0 DSP; post-route WNS +0.237 ns and WHS +0.035 ns; zero errors/critical warnings in reported build.
Reported board demo: Tile 3 attested/authorized, writes and reads 0xC0DE5A5A and reports T3 PASS; Tile 0 is refused; button 2 revokes Tile 3 and button 1 re-attests.
Package status: HARDWARE_VALIDATED=YES based on owner-reported board demo, but itemized observations pending; SOC_INTEGRATION_COMPLETE=NO; FORMAL_PROOF=NO.
KMAC is symmetric keyed authentication, not an asymmetric PQC signature. Scope any “post-quantum” statement to the selected symmetric primitive and its assumptions.
Demo nonce and secrets are fixed; TRNG is not integrated. Do not claim genuine freshness or replay resistance for the fixed-nonce demo configuration.
CPU `attest_req_o` is reported unconnected in `pq_soc_merged_core`; only RoT/button initiation is currently used.
FPGA utilization/timing is not ASIC PPA. A successful bitstream build is not proof of board operation; board operation is not formal proof.

4. G0 — Freeze project scope and owner decisions
These are owner-level decisions. The RTL team must not guess or silently change the trust model.
4.1 D1 — Can the CPU request attestation?
Current state: CPU STATUS ATTEST_REQ raises `attest_req_o`, but the signal is not connected in the merged core. RoT/button initiates attestation.
Option A: CPU may request; RoT decides. Busy requests are ignored/rate-limited by verifier busy state. Requires RTL and request/busy tests.
Option B: RoT-only initiation. CPU cannot initiate its own attestation. Contract section 8 explicitly states this. This is the recommendation for the current release.
Option C: CPU may request only for itself and only after revoke. Requires new RTL and checks.
☐  Choose D1 explicitly. Recommended for this release: Option B, RoT-only. Record in M-F1 section 8.
☐  If A or C is selected, update RTL, firmware, request/busy/error semantics and merged tests. Do not reuse B-only evidence.

11. G7 — Research-paper readiness gate
Start a paper-specific research programme only after G1–G5 are complete. G6 is required only if the research question claims ASIC physical implementation.
☐  Choose one primary research question. Do not combine runtime attestation, QoS, side-channel leakage, formal verification and physical design into one unfocused paper.
☐  Define attacker model: compromised tile capabilities, packet injection/observation, timing visibility, reset/replay capability and trusted RoT/key assumptions.
☐  Define trust boundary and security property as precise temporal assertions or mathematical invariants.
☐  Review nearest literature and establish a specific gap. Integration of PicoRV32 + SHA3/KMAC + XY mesh alone is not a novelty claim.
☐  Build a baseline and at least one ablation; compare against a credible policy/architecture, not only a strawman.
☐  Predefine experiment matrix: traffic, attacker/victim locations, packet lengths, load, repetitions, metrics and success criteria.
☐  Collect raw data, logs, scripts, source hashes and plots. Separate RTL, formal, FPGA and ASIC evidence.
☐  Report negative results and limitations. Do not claim universal Trojan detection, full CFI, side-channel/fault resistance or replay protection without direct evidence.
☐  Prepare claim-to-evidence matrix: every abstract/contribution claim maps to a figure, table, proof or test artifact.
☐  Select venue only after contribution and evidence strength are clear.

Every result records source revision, tool/version, command, configuration, test ID, result, log path and limitations.
A testbench existing is not proof it ran. Python output is not RTL evidence. Bitstream build is not board evidence. Board demo is not formal proof. FPGA PPA is not ASIC PPA.
A proposed mutant is not an executed mutant. A large test count is not proof of complete coverage.
Keep known failures and regression history. Never convert a failed run to PASS by deleting logs or changing labels.
