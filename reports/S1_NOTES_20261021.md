## 1. P7 simulation hang: root cause and fix (contract sec. 0.3)

**Symptom.** `tb_sys_f234` on `pq_noc_subsystem_p7` ran at full CPU but simulated time never advanced.

**Located through the harness launcher path** (`dual_lane.execute`: Vivado export, then the PowerShell supervisor; scratch):

| Probe | Result |
|---|---|
| TB heartbeat | heartbeats every 20 ns up to 2 µs, then none at 10 µs, at full CPU |
| `run 100ns` steps | the last completed step was at 7.1 µs |
| `run 1ns` steps | the last completed step was at 7189 ns |
| 6,000 `step` commands from 7189 ns | time stays at 7190 ns |

In the last 1,500 steps the repeating statements are:
- `rtl/dual_lane/noc_l2_auth_p7.sv`, lines 199–202 (the RX `always_comb`, slot-P replay branch);
- the P7 NI RX logic (`noc_network_interface_p7.sv`, lines 801–999);
- the endpoint (`pq_attest_endpoint.sv`, lines 127–133).

7.19 µs is the first slot-P replay, the CHALLENGE delivery.

**Root cause: a zero-delay oscillation.**
- The wrapper's RX `always_comb` read the NI's combinational `noc_rx_ready` (`ni_rr`). In the same block, it wrote the NI's `ni_rv`/`ni_rf` with default-then-override statements (`ni_rf` was assigned three times per evaluation).
- Each evaluation produced transient values that re-triggered the NI's own combinational RX logic. That logic re-triggered the wrapper block, so time could not advance.
- The values are stable, which is why the RTL combinational-loop DRC (LUTLP-1) reported 0. `synth_design -rtl` sees no loop.

**Fix** (`noc_l2_auth_p7.sv`):
- The RX and TX valid/ready paths are now single-assignment continuous logic. Flits are built by a function (`mkflit`/`len_adj`), with no intermediate values on module signals.
- No block both reads a ready and writes the matching valid/flit.
- The same rewrite was applied to the P7 subsystem's TX owner mux and to the tile-5 raw-port mux. The raw-port mux is replaced by the quarantine and merge, both continuous.

**Verified (scratch, same snapshot):** 50 µs simulated in about 25 s, with heartbeats every 10 µs. Before the fix the simulation froze at 7.19 µs.

**Regression guard:**
- Preflight rule `lint_valid_ready_comb` (`scripts/dual_lane_preflight.py`): any `always_comb` that writes a valid/flit signal and reads a ready signal is a finding.
- Test `ValidReadyCombLintTests`: the feedback form is flagged and the continuous form passes (96 harness tests OK).
- The P7 sources are clean. Four pre-existing blocks are waived, hash-pinned with reasons:
  - the B-2 `noc_l2_auth.sv` and the rev-6 subsystem, both history and not in P7;
  - the RX output blocks of the two NI variants, whose `rx_ready` comes from always-ready consumers.

## 4. F3B under P7: "control-type headers only" (justification required by Kalash, 2026-10-21 23:42)

**Claim:** in P7, tile 2 cannot emit a control-type packet, and no original check was removed.

**Why tile 2 cannot emit control traffic in P7:**
- Tile 2 is a plain `noc_network_interface_p7` built with `CONTROL_ALLOWED = 0` (`pq_noc_subsystem_p7.sv`, PLAIN generate).
  Its TX legality is `tx_msg_legal = !tx_msg_type[3] && (CONTROL_ALLOWED || !is_control(tx_msg_type))`
  (`noc_network_interface_p7.sv`:357), so a type 4-7 request raises `tx_error` and is never accepted (AM-5 mechanism).
- Tile 2's application cannot send data either: its gate is built `ATTESTABLE = 0`, so `authorized[2]` stays 0 and the
  gate blocks every data request (`noc_attest_gate.sv`, `allowed`).
- The only traffic that legitimately leaves tile 2 in P7 is the memory stand-in's reply (MEM_RD_RESP / MEM_WR_RESP, data
  types), through the F3 ownership mux.

**What the check monitors:**
- `sent2` counts a HEAD/HEAD_TAIL on `dut.tile_out[2]` with a control type (`msg_type[3:2] == 2'b01`), i.e. exactly the
  traffic that R7.4 forbids at tile 2.
- The first P7 version counted every tile-2 HEAD and therefore flagged the memory reply that F3B itself requests: a bench
  bug, not a design fault (scratch run before the fix: `F3B_APP_REFUSED tx_error_seen=1 tile2_sent=1`).

**Old vs new check sites (`sim/dual_lane/f234/tb_sys_f234_body.svh`):**

| Mode | Check | Site | Status |
|---|---|---|---|
| rev 6 (`tb_sys_f234.sv`) | `F3B_MEM_REPLY_DELIVERED` | body line 222 | unchanged |
| rev 6 (`tb_sys_f234.sv`) | `F3B_APP_PACKET_SENT` (tile 0's L2 accepts the tile-2 CHALLENGE) | body, rev-6 branch | unchanged |
| P7 (`tb_sys_f234_p7.sv`) | `F3B_MEM_REPLY_DELIVERED` | body line 203 | same rule as rev 6 |
| P7 (`tb_sys_f234_p7.sv`) | `F3B_APP_REFUSED`: `tx_error` seen at tile 2 AND no control-type HEAD leaves tile 2 | body line 204 | replaces `F3B_APP_PACKET_SENT` in P7 mode only, because in P7 the old positive outcome (tile 2 sending a CHALLENGE) is itself forbidden by R7.4 |

No check was dropped:
- The rev-6 mode keeps both original checks.
- The P7 mode keeps the same count (2). It turns the "packet sent" check into its P7 meaning: refused, and nothing illegal sent. The refusal itself is also covered by `tb_p7_refuse_grant` (`P7R_TX_REFUSED_2`).

## 5. f234_p7 M10 / AM-2 "TX bubble" on the tile-2 NI: root cause and fix (Kalash 2026-10-22, "probe first")

Observed (run 003720, f234_p7): bench 26/0 RESULT PASS, but 7 RTL `$error` "M10: TX bubble between HEAD and terminator
(AM-2)" from `GN[2].PLAIN.ni`, one per flit of every tile-2 memory response (WR_RESP 1, RD_RESP 2, suppressed replies 0).

Probe (scratch, launcher path, not evidence; 2026-10-22 11:46): tile 2 logged from each response HEAD to its terminator
with (a) the settled mid-cycle values (negedge + 2 ns, equal to what the next posedge samples), (b) the active-region
value at the posedge, (c) a bench-level concurrent property identical to `p_tx_no_bubble` on the same two signals.
Result at all 7 flagged edges: settled `noc_tx_valid` = 1, posedge value = 1, bench-level property 0 failures
(`PRB_SUMMARY settled_drops=0 sva_fails=0`), while the NI-internal `a_tx_no_bubble` still fired ("Iteration: 2").
The memory path held its request correctly: `own2_mem` = 1, `offered` = 1, `rd_gate` = 1 for the whole packet; the
reply valid (`mtv`) is not on the AM-2 path at all once the NI is in TX_HEAD (the NI serves the packet from its buffer).

Conclusion: not a protocol violation. Valid never drops for a cycle. The NI drove `noc_tx_valid` from a
default-then-override `always_comb` that also reads `tx_valid`; on tile 2 `tx_valid` (the F3 owner mux, `mtv`, `rd_gate`,
`authorized[]`) changes inside the posedge timestep, the block re-runs, and the NI-scope assertion evaluation sees the
transient default 0. Same class as the S1 hang (section 1): a valid computed by override inside a combinational block that
re-triggers within the timestep.

Fix (generator `scripts/prepare_p7ni.py`, edits at source lines 409/413/455/470/487/506/1648; the protected NI and the
dual-lane NI are unchanged): `assign noc_tx_valid = (tx_state_q == TX_HEAD) || (tx_state_q == TX_PAYLOAD) ||
(tx_state_q == TX_MAC);` (exactly the values the case statement produced), the `always_comb` writes removed, and a clocked
AM-2 check (`always_ff @(posedge clk)`, state and valid as registered at the edge) beside the unchanged `a_tx_no_bubble`.
Functionally identical; it changes the synthesized netlist identity, so the P7 subsystem OOC is re-run.

### 5a. Correction (2026-10-22 12:45): the transient explanation above is wrong

Registered run 123917 (f234_p7) with the continuous-assign NI: the original `a_tx_no_bubble` still fired 7 times, although
its consequent is now the same expression as its antecedent (a tautology), and the new clocked AM-2 check never fired.
So the failures are not a valid transient. `p7_refuse_grant` (now running via TB_INJECT, 12/12 PASS) showed the same class
on the RX side in the plain NIs: `p_discard_ready` (`noc_rx_ready` is hard 1 in RX_DISCARD) 24, `p_error_flit_consumed` 6,
`p_no_deliver_and_drop` 6. Scratch probe (launcher path, not evidence): routing only the NI's network ports through scalar
locals removed the first two classes; the third uses rx_head_valid / rx_payload_valid / rx_protocol_error, which were still
bound to packed-array elements (`rhv[g]`, `rpv[g]`) or unconnected. The same NI module inside the tile-3/4 wrappers (ports
on scalar wires) never fires, and the rev-6 subsystem never fired.

Working conclusion (tool behaviour, not proven): XSim evaluates the NI's concurrent assertions inconsistently when the NI's
ports bind directly to packed-array elements under the nested generate `GN[g].PLAIN`. Two all-scalar probes then crashed
at kernel load (probe path only), so the full-scalar form is judged in the registered path instead.

Change: every plain-NI port goes through a scalar local (pure wiring). The continuous `noc_tx_valid` stays (harmless,
S1 rule). Clocked twins (always_ff, values as registered at the edge) now sit beside AM-2 and the three RX checks, so a
real violation still fails in a form that does not depend on this evaluation. Rule for adjudication: if a clocked twin
fires, it is a real defect and a HARD STOP; the concurrent originals are never removed, waived or edited.
