Conclusion: B. RTL CONDITIONALLY CLOSED: specific verification and implementation conditions remain.

The hardware RTL is functionally complete for the approved scope and can be frozen now. No defect was found that breaks the demonstrated behaviour of the board build. Closure is conditional because (1) the measured 64-byte firmware window contains only the jump stub of the current firmware, which weakens the "firmware is measured" claim and needs your decision; (2) the demo firmware turns itself into FAIL after a few minutes without a button press; (3) the current image has not been run on the board; and (4) several verification gaps and latent corner-case defects are documented below. None of these needs a change to the protected RTL files.

7. Clock, reset and integration findings

  • One clock domain: 100 MHz board clock to MMCM (VCO 1000 MHz, inside the 600-1200 MHz range of the -1 grade) to exactly 50 MHz; BUFGs on clock and feedback.
  • Reset: asserted asynchronously while the MMCM is unlocked, released synchronously after 16 clean cycles with button 0 released; the subsystem uses a 2-flop reset bridge.
  • Asynchronous inputs (three buttons, one switch) pass through two-flop synchronisers; buttons are debounced (2^20 cycles, about 21 ms). ASYNC_REG attributes are missing (INFO).
  • report_cdc lists no crossings; check_timing: 0 unclocked pins, 0 unconstrained endpoints, 0 loops. I/O paths are declared false with justification.
  • Integration: every parent-child connection in the subsystem, core and board top was checked for order, width and polarity; bench-only hooks (TB_INJECT, BYPASS_*) are off in the build.
  • UART: 434 clocks per bit, 115,207 baud (+0.006 %). Memories: 5 x 16 KB = 20 RAMB36.

14. Final decision

Q1. Is every mandatory component of the RTL project finished?

Yes. Every approved hardware block is implemented, integrated and verified for the demonstrated behaviour.

Q2. Is there any mandatory RTL coding, debugging or verification work left?

No mandatory RTL coding. Firmware work (D-02) and one scope decision (D-01) remain; the verification gaps are improvements, not blockers.

Q3. Can we officially freeze the current RTL?

Yes, conditionally: freeze the RTL now and record D-01 and D-02 decisions. If D-01 is resolved by widening the window, that is a contract change and reopens the freeze.

Q4. Is the only remaining FPGA work the board validation?

Yes, plus the firmware timing note (D-02) for the procedure.

Q5. Can we move on to the ASIC scope without unresolved RTL debt?

Yes. The ASIC items are adaptations and physical design, not RTL debt.

B. RTL CONDITIONALLY CLOSED: specific verification or implementation conditions remain.

Why: the design is complete and the evidence for the demonstrated behaviour is current and reproducible, but the measured firmware window does not cover the program (D-01), the demo firmware times out into FAIL (D-02), the current image has not been run on the board, and verification has no coverage or formal component.
